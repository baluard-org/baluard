# SPIKE B — MV3 CSP vs WebSocket to a user-supplied relay host

**Status: resolved.** Verdict: **(a)** — an MV3 background context (Chrome service worker, Firefox event page) can open `wss://` to an *arbitrary, user-supplied* host with **no manifest CSP change and no host permissions**, in both Chrome and Firefox, *provided the extension does not tighten its default CSP with `connect-src` or `default-src`*. The feared conflict (MV3 CSP can't express a per-user host) is real but irrelevant, because the default MV3 CSP contains no `connect-src` at all.

- Researched: 2026-11-14 (Chromium 156.0.8078.47, Firefox 159.0, docs accessed same day)
- Question owner: Baluard tether design (extension ↔ user-hostable relay at e.g. `wss://relay.corp.example.com:443`)

## Empirical results (run 2026-11-14)

Method: Node 26 TLS server + hand-rolled WS upgrade (self-signed cert, `--ignore-certificate-errors` in Chromium); unpacked MV3 extension; Chromium headless via CDP (`--load-extension`); Firefox 159 headless via WebDriver BiDi `webExtension.install` + `script.evaluate` inside the extension page's realm (Firefox MV3 event pages are event-driven, so the page context — which carries the same `extension_pages` CSP — was exercised; `MOZ_REMOTE_ALLOW_SYSTEM_ACCESS=1`). Public endpoint `wss://free.blr2.piesocket.com/…` used as the "arbitrary user-supplied host" for Firefox (valid public CA cert).

### Chrome (Chromium 156, MV3 service worker)

| Variant | `extension_pages` CSP | host_permissions | Result |
|---|---|---|---|
| A | *(none — MV3 default)* | none | **WS OPEN** to `wss://localhost:9443`; `fetch('https://example.com')` → `TypeError: Failed to fetch` (host-permission gate applies to fetch, not WS) |
| B | `script-src 'self'; object-src 'self'; connect-src 'self';` | none | **WS blocked** (`'self'` = `chrome-extension://…` origin, doesn't match `wss://`) |
| C | `… connect-src wss://localhost:9443;` | none | **WS OPEN** — per-user host can be allowlisted if you ever need a static CSP |
| C2 | `… connect-src wss:;` | none | **WS OPEN** — scheme wildcard works |
| D | `script-src 'self'; object-src 'self'; default-src 'self';` | none | **WS blocked** — `connect-src` falls back to `default-src`; the trap |

### Firefox (159, MV3 event page / extension page context)

| Variant | `extension_pages` CSP | host_permissions | Result |
|---|---|---|---|
| A | *(none — MV3 default)* | none | **WS OPEN** to arbitrary public `wss://` host |
| B | `… connect-src 'self';` | none | **WS blocked** — `SecurityError`/`NS_ERROR_CONTENT_BLOCKED` thrown synchronously by `new WebSocket()` |
| D | `… connect-src wss:;` | none | **WS OPEN** |
| E | `… connect-src https://free.blr2.piesocket.com;` | none | **WS blocked** — `https:` source does not match a `wss://` URL in Firefox (unless generated from `'self'`; see `nsCSPUtils.cpp` `permitsScheme()`) |
| F/G | `… connect-src wss://host/*` or `wss://host/v3/*` | none | **WS blocked** — Firefox CSP path matching has no wildcard paths (exact path or trailing-`/` prefix only; `nsCSPHostSrc::permits`) |
| H | `… connect-src wss://free.blr2.piesocket.com/v3/1?api_key=…` (exact path+query) | none | **WS OPEN** — query string ignored in path matching |
| I | `… connect-src *;` | none | **WS OPEN** |

Note: Firefox host-permission *match patterns* are a separate mechanism and **do** support `ws:`/`wss:`/`<all_urls>` (MDN Match patterns) — but they're unnecessary for plain WS connections.

## RECOMMENDATION

For the Baluard tether design, outcome **(a)** is true on both engines: keep the manifest's `content_security_policy` key **absent (or without `connect-src`/`default-src`)** and the MV3 background context can open `wss://` to any host the user names — `wss://relay.corp.example.com:443` or a LAN/IP address — with **zero host_permissions** (WebSockets are not host-permission-gated in Chrome or Firefox, unlike `fetch()`; you only need `optional_host_permissions` if the tether also uses fetch/XHR against the relay, in which case request e.g. `https://relay.corp.example.com/*` at runtime via `permissions.request()`). **Do not add `connect-src` or `default-src` to `extension_pages`**: there is no dynamic way to update manifest CSP per user, `default-src` silently swallows WebSocket connections as its fallback (verified: bare `default-src 'self'` blocks the SW's socket), and a `connect-src` wildcard like `wss:` is legal but is a data-exfiltration-grade hole that buys nothing. If a hardening review later demands a tightened CSP, the Chrome/Firefox-agnostic escape is `connect-src wss:` or a fixed relay-list CSP — but that is option (b)/(c) territory and unnecessary for this design; both are supported if policy changes (Chrome accepts any `connect-src` value in MV3; Firefox accepts it too but only matches `wss://` host-sources without path wildcards, and `wss:`/`*` scheme-level sources always work). Two lifecycle footnotes for the tether client itself, independent of CSP: Chrome MV3 service workers need the documented 20 s WebSocket heartbeat to stay resident (Chrome 116+ behavior), and Firefox MV3 event pages suspend after ~30 s idle and are best kept alive through extension-API messaging (e.g. a `storage.session` tick or port traffic), not by assuming WebSocket traffic resets the idle timer. Shipped precedent supports the design: Alby connects its background to user-configured `wss://` Nostr-Wallet-Connect relays on Chrome MV3 with only `*://*/*` host permissions and no `connect-src` CSP. Chrome and Firefox behave the same here; the only per-engine differences that matter are the event-page-vs-service-worker lifetime rules and Firefox's stricter CSP path-wildcard matching if a CSP ever is added.
