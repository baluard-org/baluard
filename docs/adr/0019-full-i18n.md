# ADR 0019. Full Internationalization

> Status: Accepted (completed 2026-06-09)

## Context

Hardcoded user-facing text prevents consistent translation across the interface. A key present in one locale and missing in another ships silently, and users of the other language see untranslated fallback text. Baluard targets non-technical users, so the full interface, including error and toast messages, must be available in their language.

## Decision

All user-facing strings use `t()` translation keys, with no hardcoded strings in components. Coverage includes cipher schema labels, form fields, modal text, toast messages, settings sections, and the SSH key generation UI. The locale files `en.json` and `es.json` must stay key-for-key in sync.

The rule is enforced by a key-parity test that flattens the locale files to dot-path keys and fails the build when the key sets differ, so a missing translation fails at the change that introduced it. The language is chosen at vault creation and persisted in plaintext so that the login screen can be localized before unlock (ADR 0020 and ADR 0021).

Since this record was written, Portuguese (`pt.json`) was added under the same rule, and the parity test covers all three desktop files. The mobile client follows the same discipline with `StringsEn.kt`, `StringsEs.kt`, and `StringsPt.kt`; `docs/dev/translations.md` describes both.

## Consequences

User-facing text in the covered interface is managed through translation keys and the maintained locale files. Adding or changing a user-visible string requires updating every locale file in the same change.
