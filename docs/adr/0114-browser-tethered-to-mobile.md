# ADR 0114. Browser Extension Tethered to the Mobile App

> Status: Proposed (2026-11-19). Full design: `docs/designs/browser-tethered-to-mobile.md` with spike reports A (`spike-a-webcrypto-device-key.md`), B (`spike-b-mv3-csp-relay.md`), C (`spike-c-fgs-latency-battery.md`), and D (`spike-d-two-party-handshake.md`). Amends ADR 0092; reconciles with ADR 0113.

## Context

ADR 0092 wires the browser extension to the desktop daemon through the native messaging host: extension → NMH (stateless stdio relay) → 0600 daemon socket, with the desktop holding the unlock. That topology assumes a desktop instance is running and unlocked. Phone-first users do not have one: the phone is the daily driver, the desktop browser is where they fill credentials, and a desktop daemon is exactly the running process they wanted to avoid.

The mobile app hosts the runtime in-process via UniFFI (ADR 0010) and never uses the daemon socket gateway (ADR 0007). The bridge policy that gates NMH requests lives in `baluard-daemon/src/handler.rs` (routes ≈ lines 2159-3430), which mobile does not link. Firefox Android supports native messaging only for privileged GeckoView extensions, so third-party store extensions cannot use `runtime.connectNative` at all: the phone-first case needs a network transport, and MV3 service workers have WebSocket only (WebTransport is Chromium-only; BLE, NFC, and USB have no service-worker surface).

The design exploration (2026-11-14/20) resolved all four spikes favorably: non-extractable WebCrypto device keys work on Chrome and Firefox MV3 with IndexedDB persistence (Spike A, 2026-11-19); arbitrary user-supplied `wss://` relay hosts work in both browsers with no manifest CSP change and no host permissions, provided `connect-src`/`default-src` never enter the extension_pages CSP (Spike B, 2026-11-14); the Android foreground service is viable as `connectedDevice` with an adaptive keepalive, measured at ≈ 0.15 %/day net battery on WiFi at 25 s (Spike C, 2026-11-19/20); and the two-party handshake has a working prototype with forward-secrecy, replay, and impostor tests (Spike D, 2026-11-20, 8/8 green). The tether's keepalive measurements are shell-uid estimates (curl over adb), not a running Baluard service; the cellular, Doze-reconnect, and 24 h OEM-killer dogfood numbers are still pending per the protocol in the spike report. Spike C's latency figures are LAN-path measurements; relay round-trip time over the internet is part of the pending dogfood protocol.

## Decision

1. **The browser extension may tether to the Baluard Android app as its unlock authority.** The phone answers bridge requests over a WebSocket relay; direct LAN pairing is a follow-up phase (decision 8). iOS remains out of scope (no inbound sockets, outbound connections die in minutes, Safari extensions are a separate project).

2. **Work item 0 gates everything: move the bridge policy AND its dispatch out of `baluard-daemon/src/handler.rs` into `baluard-runtime`.** Policy alone is not enough: `route_bridge_request` ends by calling the daemon-only dispatcher `route_request`, whose arms (vault.get/add/update, cipher.totp_code, passkey.*, generator.*) and argument parsers (e.g. `provider_assert_args`) also live in handler.rs, and `GatewayRequest`/`GatewayResponse` are prost types generated in baluard-daemon, which runtime and uniffi do not depend on. Work item 0 therefore includes: a transport-neutral request/response type (proto moved to the shared `proto/` crate or an equivalent), a dispatch trait implemented by the daemon (socket path, unchanged behavior) and by mobile (UniFFI methods it already exposes, e.g. `get_cipher`, `passkey_provider_assert`), the argument parsers, the bridge allowlist/read-cap/write-field gates, and the tests at handler.rs:8800-9600 (they call private functions and must be re-parented). Linking is feasible: baluard-uniffi already depends on baluard-runtime and `VaultState::bridge_write_allowed` is already there. Real size is well above 1k lines. Note: `bridge.request_unlock` assumes a desktop poller; the phone replaces it with push-over-session delivery.

3. **Channel security: a two-party ephemeral handshake with explicit replay defense (Spike D, resolved 2026-11-20).** Sender-ephemeral HPKE `OpModeS::Auth` does NOT give forward secrecy (a later phone-static-key leak decrypts every recorded handshake) and is open to key-compromise impersonation; a first ciphertext under static keys is replayable within any timestamp window; and an HPKE Auth channel would force a new JS HPKE dependency (no WebCrypto HPKE API exists). The channel is therefore the Spike-D "webnative" construction (Noise-KX-flavored): both sides contribute fresh ephemeral X25519 keys; session keys = HKDF over the triple DH blend (DH(eI,eR), DH(eI,sR), DH(sI,eR)) with the full transcript including a fresh server nonce; the phone signs msg2 with its pinned Ed25519 signing key (its X25519 static key enters only the DH blend) and the extension signs the transcript with the device Ed25519 key; the phone executes NOTHING before its nonce is in the transcript and the initiator's first frame echoes it (replayed first frames always fail the echo). Frames are AES-256-GCM with transcript hash + per-direction sequence counter + timestamp bound into the AAD; counters are in-memory per session. The construction is custom, not a stock Noise pattern (the transcript signing with Ed25519 has no Noise equivalent), so there is no off-the-shelf audited implementation to adopt: the production handshake code MUST undergo a dedicated third-party security review before this ADR moves to Accepted, and the review should first check whether a stock Noise pattern (XX or IK, with the nonce echo as an application-layer step) can replace it. The JS side uses WebCrypto primitives only (zero new dependencies). The prototype tests (8/8 green, `docs/designs/spike-d-src/`) cover the Rust-to-Rust handshake only; the JS implementation and the AEAD frame layer are untested implementation work.

4. **Pairing: extension displays a QR code, the phone scans it.** The QR carries a one-time pairing secret with a short TTL (120 s), shown once; PAKE is rejected for v1 (the QR is shown on the browsing machine, so a screenshot or shoulder-surf yields a single-use secret valid for 120 s that is still useless without on-phone confirmation, which shows browser name and IP). 128-bit rendezvous ID, proof of possession, and mutual pinning during the ceremony: the extension pins the phone's Ed25519 signing key and X25519 static key; the phone pins the device's Ed25519 signing key and X25519 static key. Multi-phone and multi-browser pairs are keyed by pairing ID with revocation and last-seen in the phone's settings surface.

5. **The extension holds one secret: a non-extractable WebCrypto credential pair, persisted in IndexedDB (Spike A).** Roles are explicit (Spike D webnative construction): a static X25519 key for the DH blend plus an Ed25519 signing key for device authentication; the phone holds the same two roles. Both primitives are WebCrypto-native, so there is no new JS crypto dependency to audit or pin. Chrome < 137 lacks Ed25519 (available since Chrome 137 per Spike A); the fallback is a P-256 ECDSA signing key in place of Ed25519, or explicit version gating — X25519 itself is available since Chrome 133. No vault secret, key, token, or master password ever enters extension storage; `chrome.storage.sync` is banned by lint for pairing material. The credential is a sensitive, remote-capable bearer credential valid until revoked, not "just a device key". It is bounded by a DAILY read cap on every bridge action including `bridge.match` (uncapped today in handler.rs:2697-2704, a metadata-enumeration hole that the same fix closes for the desktop path too) and by revocation; the burst-only 30/60 s cap on vault.get does not protect it. The caps are specified in decision 5a; `bridge.match` alone never auto-revokes.

5a. **Read-cap design (per pairing; the caps and counters live in the extracted bridge policy so daemon and phone share one code path).** `bridge.match` is counted per DISTINCT registrable domain (via the existing uri-match machinery), never per call: rolling 24 h limits of 500 distinct domains probed, 150 distinct domains matched, and 60 new distinct domains per minute (a session restore opens ~50 tabs); repeat lookups of an already-counted domain are free; exceeding any limit THROTTLES (`match-throttled` error, badge shows empty, popup shows "lookups paused") — throttling never revokes, and any throttle event raises a rate-limited phone notification ("Unusual lookups from <browser>"). Auto-revoke is fed ONLY by secret-yielding actions: `vault.get` + `cipher.totp_code` combined (totp_code is allowlisted but uncharged today — a gap) at 200 per rolling 24 h, plus the existing 30/60 s burst on `vault.get`/`passkey.provider_assert` converted to a sliding window. Escalation (tether only): throttle trips on 3 separate days → the phone pauses the pairing and requires biometric confirmation to resume; it does not revoke. The phone persists counters date-keyed in app-private storage (OEM task-killer restarts reset memory); the daemon keeps them in memory as the BridgeRegistry does today. Desktop users get the same limits (5-10x above normal browsing of ~100-200 distinct domains/day) — noted in release notes.

6. **The relay is untrusted and user-hostable, with small bounded state.** A rendezvous relay (≈ 500-1000 lines) holds only in-flight rendezvous state (IDs, rate-limit counters); it sees rendezvous IDs, client IP addresses, connect times, ciphertext sizes, and timing; nothing else. The PRIMARY self-host path is a `baluard relay` CLI subcommand: the CLI already ships in the apt/rpm/dnf trees, so self-hosting is install + one command behind systemd, with the optional docker image kept for VPS-only users; both serve the same wire protocol. TLS at the relay is required even though the envelope is E2E (Firefox `upgrade-insecure-requests` upgrades `ws://` to `wss://`, Spike B): tailscale serve in front (tailnet members only; needs HTTPS certificates enabled once in the tailnet admin), Caddy in front, or native ACME in the CLI later. First-party Tailscale Funnel support extends the CLI relay to machines WITHOUT a public IP (a home server or NAS behind CGNAT now qualifies): the box runs `baluard relay` plus Tailscale with Funnel, the extension needs no Tailscale (the funnel URL is public), and the QR carries the funnel URL as the relay endpoint. Both ends dial the same relay endpoint from the QR: the extension reaches it from the browsing machine, and the phone dials out to it over WSS; the phone never needs Tailscale for the funnel path. If phone and browser are both on a tailnet, the QR may carry the tailnet address instead, and then both ends need Tailscale. Funnel terminates TLS at the user's device with a valid ts.net cert issued through Tailscale's control plane (a configuration fact, not a guarantee against Tailscale; security does not depend on it because the E2E channel is authenticated by pinned keys, so a TLS-terminating party can only drop traffic or read metadata). Tailscale's Funnel ingress is a SECOND metadata holder: it sees client IP addresses, the ts.net hostname, connection timing, and byte counts in addition to what the relay operator sees, and "no Baluard-operated server sees vault data" stays true. Funnel needs a one-time tailnet-admin config (HTTPS certificates + funnel node attribute) and does NOT run on the phone itself (Funnel requires the Tailscale CLI; the Android and iOS apps do not support it), so the funnel is a reachability add-on for the relay box, never a phone endpoint. The relay must sit somewhere with inbound reachability (VPS, office box, NAS port forward, always-on tailnet node, or a Funnel-fronted box with no public IP); on a shared tailnet the relay never touches the public internet. A Baluard-hosted relay is opt-in, and shipping it is gated on the metadata-processor decision (GDPR, retention, uptime commitment) recorded in the design doc. MV3 CSP stays free of `connect-src` (Spike B): self-hosted relay hostnames need no manifest changes.

7. **Mobile: `connectedDevice` foreground service (Spike C).** `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_CONNECTED_DEVICE` + `POST_NOTIFICATIONS`, plus a `CHANGE_WIFI_STATE`-style prerequisite, started only from an explicit user action, honest persistent notification with one-tap stop, never from `BOOT_COMPLETED`. The merged manifests already carry plain `FOREGROUND_SERVICE` and `RECEIVE_BOOT_COMPLETED` via androidx.work; the tether service must not register boot receivers and must not start or keep the iroh node (ADR 0113) alive — the FGS is bridge-only. Fallbacks if Play review pushes back, in order: active-session framing, then `specialUse`, then `dataSync` with stop-on-timeout. The F-Droid flavor needs no Play declaration. Keepalive is adaptive: 25 s on WiFi/screen-on, 60-120 s background WiFi, 60-300 s cellular; Doze is a disconnect event ("authority offline"). The battery-optimization exemption is effectively required for the primary use case (desk phone in deep Doze; the spike showed no network reaches even shell-uid traffic in deep idle), so it is offered as a first-class step of the tether onboarding, in plain language (its acceptable-use table covers peripheral companion apps). Per-ceremony phone biometric step-up is retained, with the locked-phone state machine (disconnected / handshaking / paired_locked / paired_unlocked / needs_biometric) and unlock-prompt rate limiting from the design doc as the shipped behavior. Keepalive and battery numbers are shell-uid estimates until the dogfood protocol in the spike report runs.

8. **Phasing.** v1 ships internet-relay tether as primary, gated on work item 0, the channel and pairing specs (channel scheme resolved by Spike D; production handshake review per decision 3 is the remaining channel gate), the hosted-relay GDPR decision, and the resolved spikes. LAN direct pairing is NOT in v1: it is unproven on the browser side (Firefox's `upgrade-insecure-requests` upgrades `ws://`, a phone-served self-signed endpoint cannot be pinned from the WebSocket API, and Android 17 makes `ACCESS_LOCAL_NETWORK` mandatory at targetSdk 37); it moves to a follow-up phase behind its own spike. Later: relay hardening from operation, Safari/iOS evaluation. The feature is off by default; pairing revocation is phone-local and immediate; when the relay is down the feature degrades to "phone unreachable", never to secret exposure. Play data-safety declarations and the privacy page must be updated before any hosted-relay submission (today they declare no data collected).

## Amendments to ADR 0092

- Line 9 ("Baluard has no application server") reads after this ADR: **no Baluard-operated server sees vault data.** The optional relay is metadata-only infrastructure, and the self-hosted CLI relay keeps the stance testable. The rest of line 9 ("Browser access must use the unlocked desktop daemon … with the desktop holding the unlock") is superseded by this ADR for tethered sessions: the phone holds the unlock.
- Line 57 ("Extension JavaScript touches no secrets") reads after this ADR: **extension JavaScript touches no vault secrets.** It holds the credential pair of decision 5, which is sensitive, remote-capable, and valid until revoked; the wording must not be read as "the browser holds nothing sensitive".
- The following statements of ADR 0092 are also superseded for tethered sessions and are amended by this ADR: the v1 non-goals "No communication with any remote service from the extension" and "No mobile client" (the tethered extension talks to exactly one rendezvous relay of the user's choice); "rides an already-unlocked daemon" and the desktop-initiated pairing ceremony (the phone initiates consent; the QR carries a one-time secret the desktop displays); and "needs the desktop running and unlocked". Desktop-daemon tethering is unchanged and remains the default path.
- Threat model, concrete targets, not "a new entry" somewhere: (1) new item T17 in `docs/security/threat-model.md`: browser-stored non-extractable credential pair — remote-capable bearer credential, profile-directory copy risk (Bugzilla 1556794), bounded by daily read cap, pairing revocation, and phone-side consent; (2) edit the threat-model invariant "short-lived: tokens die on lock" to carve out the device credential with its revocation bound; (3) add the row to the threat-model "Brokered Capabilities, Never Bearer Secrets" table documenting the one deliberate deviation; (4) extend ADR 0092's threat list with the same item; (5) note the credential in ADR 0024's condensed record.

## Reconciliation with ADR 0113

ADR 0113 commits mobile to foreground-only P2P sync, and ADR 0114 reverses that for one component only: the tether bridge runs as a foreground service while the user has browser access enabled, and the FGS must not start or keep the iroh node alive (bridge-only, enforced in the service implementation). The two transports do not merge: iroh (0113) carries vault sync between enrolled vault devices, authenticated against enrolled device public keys in the git-synced device history; the tether relay (0114) carries request/response unlock traffic between a browser and one phone, where the browser device credential is NOT a vault-enrolled device and its revocation is phone-local, not part of the git device history. An application-layer envelope is required because MV3 service workers cannot run QUIC. Two relays exist for two different protocol families; consolidation is rejected until an iroh-compatible browser transport exists. Both ADRs are Proposed; neither is bound by the other until Accepted.

## Consequences

- Phone-first users get browser autofill and passkeys against the phone's unlocked state, cross-network, without running a desktop daemon.
- The bridge policy AND its dispatch become one implementation shared by socket and network transports, ending the daemon-only split before it accretes a third caller.
- The extension storage posture changes once, deliberately, with the named threat-model edits above; everything else from ADR 0092 (no keys, no tokens, no master password in browser memory) holds unchanged.
- The relay is new attack surface bounded to denial of service; relay-hostile framing in the design doc degrades the feature to "phone unreachable", never to secret exposure. Self-hosting is one command on a machine the user already runs (`baluard relay`, shipped in the existing package trees; the image stays optional for VPS-only users).
- Battery cost on WiFi is estimated negligible (≈ 0.15 %/day net, shell-uid measurement) and confirmed by the dogfood protocol before general availability; cellular is bounded by the adaptive keepalive rather than a fixed 25 s ping; OEM task-killer churn is designed for via cheap per-session re-handshakes.
- Play review carries residual risk around the always-on foreground service; the fallback ladder and the pairing-flow declaration video are prepared up front, and the data-safety/privacy updates are a release gate.
- `bridge.match` loses its uncapped status as part of the same work item, closing the metadata-enumeration hole for the desktop path too; the cap is badge-scale or per-distinct-domain and never auto-revokes on `bridge.match` alone.

## Appendix A: production handshake review scope

Everything below must pass a dedicated third-party review of the production handshake code before this ADR moves to Accepted (decision 8 gate).

1. Equivalence first: show whether a stock Noise pattern (IK or XX, nonce echo as an application step) gives the same properties; if it does, adopt it and delete the custom code.
2. Transcript binding: every message and frame key derives from a hash over protocol label and version, pairing ID, rendezvous ID, both ephemeral publics, both static publics, and the phone nonce. The relay URL is deliberately NOT bound: the relay is untrusted, and a pairing may be reached through several equivalent endpoints (public URL, funnel URL, tailnet address). Nothing the relay can alter stays outside the transcript except its own address.
3. Signature domain separation: the Ed25519 signature input has a fixed context string and role tag (initiator or responder); a msg2 signature cannot be reused as a msg3 signature; no unauthenticated field exists.
4. DH hygiene: reject all-zero and low-order X25519 outputs; ephemerals are single-use and wiped after the DH; in JS, non-extractable ephemerals are never reused across sessions or tabs; public keys are derived from secrets, never by reinterpreting secret bytes (Spike D finding 3).
5. Key schedule: HKDF salt, info, and output labels differ per purpose and direction (two AES keys, separate nonce/IV derivation); no key reuse between handshake and data frames.
6. Replay: the phone sends a fresh 32-byte CSPRNG nonce per attempt; msg3 must echo it; the phone executes nothing before msg3 verifies and leaks no distinct error; nonce state is single-use and expires within 10 s.
7. Downgrade and version: protocol version and suite ID are inside the transcript; no negotiation path to a weaker mode; the P-256 ECDSA signing fallback is a distinct suite ID.
8. Forward secrecy: reproduce the Spike D tests in production code, plus a case where only the phone static key leaks.
9. KCI: state what a leak of the phone static key or of the device credential enables; the triple DH plus signatures must keep impersonation of the other side requiring its own key.
10. AEAD frames: AES-256-GCM; unique counter-based IV per direction, never random; counter bound in the AAD; strict next-expected sequence with a stated reorder window; counter limit forces rekey long before 2^32 messages; frame size cap enforced before decrypt.
11. Timestamps: allowed skew stated (30 s); skew failure is distinguishable from auth failure only in the user UI; clock changes cannot rewind counters.
12. Pre-parse gate: verify, decrypt, and check pairing, allowlist, and size before any protobuf or JSON parsing.
13. Pairing ceremony: one-time secret entropy >= 128 bits, 120 s TTL, single use, 3-attempt limit, constant-time compare, the secret is never reused as key material; relay squat and race behavior defined; the QR may carry one or more relay endpoints and the phone dials the first that answers; pinning covers all four keys; re-pair after rotation is unambiguous.
14. Revocation: on revoke, live sessions close immediately and no later handshake succeeds with the revoked keys.
15. JS side: WebCrypto only, non-extractable credentials, X25519 derive uses `{name:"X25519", public: ...}` (Spike A); no `Math.random`; cross-implementation test vectors against the Rust code.
16. Relay hostility tests: drop, delay, reorder, duplicate, truncate, swap peers, and replay msg1 or msg3 across sessions; each ends in "phone unreachable" or a rejected frame, never an executed request.
17. Zeroization: all Rust key material zeroizes on drop; panic paths and error-path logging leak no secrets.
