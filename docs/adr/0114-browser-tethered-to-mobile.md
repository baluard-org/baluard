# ADR 0114. Browser Extension Tethered to the Mobile App

> Status: Accepted (2026-11-20), with one open design gate: Appendix A item 13 (pairing handshake pattern) blocks build list item 4. Full design: `docs/designs/browser-tethered-to-mobile.md` with spike reports A (`spike-a-webcrypto-device-key.md`), B (`spike-b-mv3-csp-relay.md`), C (`spike-c-fgs-latency-battery.md`), D (`spike-d-two-party-handshake.md`), and E (`spike-e-snow-wasm.md`). Amends ADR 0092; reconciles with ADR 0113. The Appendix A design review completed 2026-11-20 (verdict CHANGE-FIRST, blockers folded; review record at the end of Appendix A); the Appendix A items gated on production code are implementation gates for build list items 1 and 3.

## Context

ADR 0092 wires the browser extension to the desktop daemon through the native messaging host: extension → NMH (stateless stdio relay) → 0600 daemon socket, with the desktop holding the unlock. That topology assumes a desktop instance is running and unlocked. Phone-first users do not have one: the phone is the daily driver, the desktop browser is where they fill credentials, and a desktop daemon is exactly the running process they wanted to avoid.

The mobile app hosts the runtime in-process via UniFFI (ADR 0010) and never uses the daemon socket gateway (ADR 0007). The bridge policy that gates NMH requests lives in `baluard-daemon/src/handler.rs` (routes ≈ lines 2159-3430), which mobile does not link. Firefox Android supports native messaging only for privileged GeckoView extensions, so third-party store extensions cannot use `runtime.connectNative` at all: the phone-first case needs a network transport, and MV3 service workers have WebSocket only (WebTransport is Chromium-only; BLE, NFC, and USB have no service-worker surface).

The design exploration (2026-11-14/20) resolved all five spikes favorably: non-extractable WebCrypto device keys work on Chrome and Firefox MV3 with IndexedDB persistence (Spike A, 2026-11-19); arbitrary user-supplied `wss://` relay hosts work in both browsers with no manifest CSP change and no host permissions, provided `connect-src`/`default-src` never enter the extension_pages CSP (Spike B, 2026-11-14); the Android foreground service is viable as `connectedDevice` with an adaptive keepalive, measured at ≈ 0.15 %/day net battery on WiFi at 25 s (Spike C, 2026-11-19/20); and the two-party handshake exists first as a custom prototype (Spike D, 2026-11-20, 8/8 green) and then as the adopted stock Noise handshake via `snow` — Spike E proved the IK shape end-to-end over WebSocket from a Chromium service worker and a Firefox event page with the crypto compiled to WASM, and the 2026-11-20 third-party design review fixed production at the NK pattern (decision 3). The tether's keepalive measurements are shell-uid estimates (curl over adb), not a running Baluard service; the cellular, Doze-reconnect, and 24 h OEM-killer dogfood numbers are still pending per the protocol in the spike report. Spike C's latency figures are LAN-path measurements; relay round-trip time over the internet is part of the pending dogfood protocol.

## Decision

1. **The browser extension may tether to the Baluard Android app as its unlock authority.** The phone answers bridge requests over a WebSocket relay; direct LAN pairing is a follow-up phase (decision 8). iOS remains out of scope (no inbound sockets, outbound connections die in minutes, Safari extensions are a separate project).

2. **Work item 0 gates everything: move the bridge policy AND its dispatch out of `baluard-daemon/src/handler.rs` into `baluard-runtime`.** Policy alone is not enough: `route_bridge_request` ends by calling the daemon-only dispatcher `route_request`, whose arms (vault.get/add/update, cipher.totp_code, passkey.*, generator.*) and argument parsers (e.g. `provider_assert_args`) also live in handler.rs, and `GatewayRequest`/`GatewayResponse` are prost types generated in baluard-daemon, which runtime and uniffi do not depend on. Work item 0 therefore includes: a transport-neutral request/response type (proto moved to the shared `proto/` crate or an equivalent), a dispatch trait implemented by the daemon (socket path, unchanged behavior) and by mobile (UniFFI methods it already exposes, e.g. `get_cipher`, `passkey_provider_assert`), the argument parsers, the bridge allowlist/read-cap/write-field gates, and the tests at handler.rs:8800-9600 (they call private functions and must be re-parented). Linking is feasible: baluard-uniffi already depends on baluard-runtime and `VaultState::bridge_write_allowed` is already there. Real size is well above 1k lines. (Status: DONE, 2026-11-20 — `baluard-runtime/src/bridge_policy.rs` behind the `BridgeDispatcher` trait, proto types in the shared `baluard-proto` crate, `MobileDispatcher` as the second implementer; 441 tests green in the isolated container.) Note: `bridge.request_unlock` assumes a desktop poller; the phone replaces it with push-over-session delivery.

3. **Channel security: stock Noise NK via `snow`, with a mandatory device-signature first frame (Spikes D and E; pattern fixed by the 2026-11-20 design review).** Sender-ephemeral HPKE `OpModeS::Auth` does NOT give forward secrecy (a later phone-static-key leak decrypts every recorded handshake), is open to key-compromise impersonation, and its first ciphertext under static keys is replayable within any timestamp window; a new JS HPKE dependency is also out (no WebCrypto HPKE API exists). Spike D fixed those defects with a custom "webnative" handshake; Spike E proved a stock Noise pattern works end-to-end in the browser (8/8 native tests, then handshakes from a Chromium 156 service worker and a Firefox 159 event page, crypto compiled to `wasm32-unknown-unknown` at 103,108 B raw / 39,539 B gzip plus ~2 KB glue, pure-Rust resolver, no ring in the wasm graph), and the third-party design review (2026-11-20) fixed the production pattern at `Noise_NK_25519_ChaChaPoly_BLAKE2s` via `snow`: IK's initiator-static authentication is KCI-vulnerable (Noise spec §7.7 grades IK msg1 source level 1, static-static), and a browser-held Noise static cannot stay non-extractable (snow needs raw key bytes synchronously; `deriveBits` is async), so the extension initiates with an ephemeral only — the Spike-D webnative code is not carried into production (its sources stay under `docs/designs/spike-d-src/` as evidence), and the spike's wasm, CSP, WebSocket, transport-frame, and nonce-echo evidence carries to NK while its IK-specific tests (impostor static, unpinned initiator) do not; no spike test covers the device signature or the msg1 timestamp and ephemeral cache (IK msg1 minus the `ss` term). The phone runs native snow behind UniFFI; the extension runs the same snow as wasm, so one implementation serves both ends. The phone is authenticated by its pinned X25519 static (NK msg2, KCI-resistant per spec §7.7); the extension is authenticated SOLELY by its Ed25519/P-256 device signature, which is MANDATORY and rides transport frame 1 (counter 0) together with the nonce echo, bound to the Noise handshake hash (`get_handshake_hash()`) with a fixed context string and role tag (Appendix A item 3); the phone executes NOTHING until the AEAD, echo, and signature all verify, through one shared failure path. Replay defense is layered: msg1 carries only version + unix-ms timestamp (30 s skew; msg1 confidentiality is level 2 per spec §7.7, so nothing sensitive rides it); the responder keeps a 60 s cache of seen initiator ephemerals checked before any DH and allows one in-flight handshake per rendezvous; the fresh 32-byte CSPRNG nonce rides the msg2 payload and the echo at counter 0 is defense in depth (Noise's fresh responder ephemeral already fails stale-frame AEAD, and counter 0 is single-use); a 10 s deadline from msg2 to frame 1 destroys the state. Frames are Noise transport messages (ChaCha20-Poly1305 — the recorded exception to the repo's AES-256-GCM invariant; per-direction keys from `Split()`; the implicit 64-bit counter is the nonce), NOT custom AES-GCM with a hand-built AAD list: direction, counter, and transcript binding are structural in Noise, pairing/rendezvous/version/suite bind via the prologue (`"baluard-tether/v1" || suite_id || pairing_id || rendezvous_id`, relay URL deliberately excluded), and timestamp/action ride inside the encrypted envelope. The relay can drop, duplicate, and reorder, so the strict next-expected per-direction counter is the enforcement — NO reorder window (WebSocket ordering only prevents spurious failures on the honest path); any Decrypt failure or oversize frame closes the session with one uniform close code; a session hard cap (2^20 frames or 24 h) closes and re-handshakes (~1 ms on wake) instead of running rekey state. The extension CSP gains `script-src 'self' 'wasm-unsafe-eval'` while `default-src` and `connect-src` stay banned; Spike E confirmed a custom `extension_pages` CSP replaces Firefox's default wholesale, so `upgrade-insecure-requests` disappears and the ws:// fallback is not force-upgraded. snow standing: Trail of Bits audited (report 2024-03, funded by 1Password; 8 of 10 findings resolved per the 1Password post of 2026-06-16, including the medium nonce-handling flaw and the PSK panic; 2 informational items open per that post), and production MUST pin the snow release containing those fixes once mapped (open task); the Noise patterns are symbolically verified (ProVerif, Noise Explorer, eprint 2018/766), and WireGuard ships IKpsk2 at scale (precedent for Noise in production, not for NK). Honest limits: one session per wasm module (re-init on every service-worker wake), Firefox wss with a trusted CA unproven (no certutil on the test host), the PSK upgrade (NKpsk2) untested as a follow-up decision, and zeroization of the wasm linear memory unaudited (item 17 tasks). Prototype evidence and wire shape: `spike-e-snow-wasm.md` and `spike-e-src/`.

4. **Pairing: extension displays a QR code, the phone scans it.** The QR carries a one-time pairing secret with a short TTL (120 s), shown once; PAKE is rejected for v1 (the QR is shown on the browsing machine, so a screenshot or shoulder-surf yields a single-use secret valid for 120 s that is still useless without on-phone confirmation, which shows browser name and IP). 128-bit rendezvous ID, proof of possession, and pinning during the ceremony: the extension pins the phone's Ed25519 signing key and X25519 Noise static (one phone Noise static per pairing); the phone pins the extension's Ed25519 signing key (the browser holds no Noise static — decision 3). Multi-phone and multi-browser pairs are keyed by pairing ID with revocation and last-seen in the phone's settings surface.

5. **The extension holds one secret: a non-extractable WebCrypto signing credential, persisted in IndexedDB (Spike A).** Roles are explicit (decision 3, NK construction per the 2026-11-20 review): the extension holds ONE WebCrypto key, the Ed25519 signing credential for device identity; the phone holds a device Ed25519 signing key plus one X25519 Noise static per pairing (design doc, multi-phone rules), both native. The credential is generated and held through WebCrypto, so there is no new JS crypto dependency for the credential; channel cryptography lives in the audited snow wasm module, whose per-session X25519 ephemerals never leave the wasm boundary. Chrome < 137 lacks Ed25519 (available since Chrome 137 per Spike A); the fallback is a P-256 ECDSA signing key in place of Ed25519, or explicit version gating. No vault secret, key, token, or master password ever enters extension storage; `chrome.storage.sync` is banned by lint for pairing material. The credential is a sensitive, remote-capable bearer credential valid until revoked, not "just a device key". It is bounded by a DAILY read cap on every bridge action including `bridge.match` (uncapped today in handler.rs:2697-2704, a metadata-enumeration hole that the same fix closes for the desktop path too) and by revocation; the burst-only 30/60 s cap on vault.get does not protect it. The caps are specified in decision 5a; `bridge.match` alone never auto-revokes.

5a. **Read-cap design (per pairing; the caps and counters live in the extracted bridge policy so daemon and phone share one code path).** `bridge.match` is counted per DISTINCT registrable domain (via the existing uri-match machinery), never per call: rolling 24 h limits of 500 distinct domains probed, 150 distinct domains matched, and 60 new distinct domains per minute (a session restore opens ~50 tabs); repeat lookups of an already-counted domain are free; exceeding any limit THROTTLES (`match-throttled` error, badge shows empty, popup shows "lookups paused") — throttling never revokes, and any throttle event raises a rate-limited phone notification ("Unusual lookups from <browser>"). Auto-revoke is fed ONLY by secret-yielding actions: `vault.get` + `cipher.totp_code` combined (totp_code is allowlisted but uncharged today — a gap) at 200 per rolling 24 h, plus the existing 30/60 s burst on `vault.get`/`passkey.provider_assert` converted to a sliding window. Escalation (tether only): throttle trips on 3 separate days → the phone pauses the pairing and requires biometric confirmation to resume; it does not revoke. The phone persists counters date-keyed in app-private storage (OEM task-killer restarts reset memory); the daemon keeps them in memory as the BridgeRegistry does today. Desktop users get the same limits (5-10x above normal browsing of ~100-200 distinct domains/day) — noted in release notes.

6. **The relay is untrusted and user-hostable, with small bounded state.** A rendezvous relay (≈ 500-1000 lines) holds only in-flight rendezvous state (IDs, rate-limit counters); it sees rendezvous IDs, client IP addresses, connect times, ciphertext sizes, and timing; nothing else. The PRIMARY self-host path is a `baluard relay` CLI subcommand: the CLI already ships in the apt/rpm/dnf trees, so self-hosting is install + one command behind systemd, with the optional docker image kept for VPS-only users; both serve the same wire protocol. TLS at the relay is required even though the envelope is E2E (Firefox `upgrade-insecure-requests` upgrades `ws://` to `wss://`, Spike B): tailscale serve in front (tailnet members only; needs HTTPS certificates enabled once in the tailnet admin), Caddy in front, or native ACME in the CLI later. First-party Tailscale Funnel support extends the CLI relay to machines WITHOUT a public IP (a home server or NAS behind CGNAT now qualifies): the box runs `baluard relay` plus Tailscale with Funnel, the extension needs no Tailscale (the funnel URL is public), and the QR carries the funnel URL as the relay endpoint. Both ends dial the same relay endpoint from the QR: the extension reaches it from the browsing machine, and the phone dials out to it over WSS; the phone never needs Tailscale for the funnel path. If phone and browser are both on a tailnet, the QR may carry the tailnet address instead, and then both ends need Tailscale. Funnel terminates TLS at the user's device with a valid ts.net cert issued through Tailscale's control plane (a configuration fact, not a guarantee against Tailscale; security does not depend on it because the E2E channel is authenticated by pinned keys, so a TLS-terminating party can only drop traffic or read metadata). Tailscale's Funnel ingress is a SECOND metadata holder: it sees client IP addresses, the ts.net hostname, connection timing, and byte counts in addition to what the relay operator sees, and "no Baluard-operated server sees vault data" stays true. Funnel needs a one-time tailnet-admin config (HTTPS certificates + funnel node attribute) and does NOT run on the phone itself (Funnel requires the Tailscale CLI; the Android and iOS apps do not support it), so the funnel is a reachability add-on for the relay box, never a phone endpoint. The relay must sit somewhere with inbound reachability (VPS, office box, NAS port forward, always-on tailnet node, or a Funnel-fronted box with no public IP); on a shared tailnet the relay never touches the public internet. Baluard does not operate a hosted relay (decided 2026-11-20): hosting one would make Baluard a GDPR data processor for relay metadata (client IPs, rendezvous IDs, timing) with privacy-policy, retention, and uptime commitments, and self-hosting already covers the need. Every relay is user-operated; the hosted option was considered and rejected. MV3 CSP stays free of `connect-src` (Spike B): self-hosted relay hostnames need no manifest changes.

7. **Mobile: `connectedDevice` foreground service (Spike C).** `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_CONNECTED_DEVICE` + `POST_NOTIFICATIONS`, plus a `CHANGE_WIFI_STATE`-style prerequisite, started only from an explicit user action, honest persistent notification with one-tap stop, never from `BOOT_COMPLETED`. The merged manifests already carry plain `FOREGROUND_SERVICE` and `RECEIVE_BOOT_COMPLETED` via androidx.work; the tether service must not register boot receivers and must not start or keep the iroh node (ADR 0113) alive — the FGS is bridge-only. Fallbacks if Play review pushes back, in order: active-session framing, then `specialUse`, then `dataSync` with stop-on-timeout. The F-Droid flavor needs no Play declaration. Keepalive is adaptive: 25 s on WiFi/screen-on, 60-120 s background WiFi, 60-300 s cellular; Doze is a disconnect event ("authority offline"). The battery-optimization exemption is effectively required for the primary use case (desk phone in deep Doze; the spike showed no network reaches even shell-uid traffic in deep idle), so it is offered as a first-class step of the tether onboarding, in plain language (its acceptable-use table covers peripheral companion apps). Per-ceremony phone biometric step-up is retained, with the locked-phone state machine (disconnected / handshaking / paired_locked / paired_unlocked / needs_biometric) and unlock-prompt rate limiting from the design doc as the shipped behavior. Keepalive and battery numbers are shell-uid estimates until the dogfood protocol in the spike report runs.

8. **Phasing.** v1 ships internet-relay tether as primary, gated on work item 0, the channel and pairing specs (channel scheme resolved by Spikes D and E and the 2026-11-20 design review — Appendix A review record; the pairing handshake pattern is still an open spec per Appendix A item 13), and the resolved spikes. LAN direct pairing is NOT in v1: it is unproven on the browser side (Firefox's `upgrade-insecure-requests` upgrades `ws://`, a phone-served self-signed endpoint cannot be pinned from the WebSocket API, and Android 17 makes `ACCESS_LOCAL_NETWORK` mandatory at targetSdk 37); it moves to a follow-up phase behind its own spike. Later: relay hardening from operation, Safari/iOS evaluation. The feature is off by default; pairing revocation is phone-local and immediate; when the relay is down the feature degrades to "phone unreachable", never to secret exposure. Play data-safety declarations and the privacy page stay as they are (today they declare no data collected): Baluard operates no relay, so the declarations stay true.

## Amendments to ADR 0092

- Line 9 ("Baluard has no application server") reads after this ADR: **no Baluard-operated server sees vault data.** The optional relay is metadata-only infrastructure, and the self-hosted CLI relay keeps the stance testable. The rest of line 9 ("Browser access must use the unlocked desktop daemon … with the desktop holding the unlock") is superseded by this ADR for tethered sessions: the phone holds the unlock.
- Line 57 ("Extension JavaScript touches no secrets") reads after this ADR: **extension JavaScript touches no vault secrets.** It holds the signing credential of decision 5, which is sensitive, remote-capable, and valid until revoked; the wording must not be read as "the browser holds nothing sensitive".
- The following statements of ADR 0092 are also superseded for tethered sessions and are amended by this ADR: the v1 non-goals "No communication with any remote service from the extension" and "No mobile client" (the tethered extension talks to exactly one rendezvous relay of the user's choice); "rides an already-unlocked daemon" and the desktop-initiated pairing ceremony (the phone initiates consent; the QR carries a one-time secret the desktop displays); and "needs the desktop running and unlocked". Desktop-daemon tethering is unchanged and remains the default path.
- Threat model, concrete targets, not "a new entry" somewhere: (1) new item T17 in `docs/security/threat-model.md`: browser-stored non-extractable signing credential — remote-capable bearer credential, profile-directory copy risk (Bugzilla 1556794), bounded by daily read cap, pairing revocation, and phone-side consent; (2) edit the threat-model invariant "short-lived: tokens die on lock" to carve out the device credential with its revocation bound; (3) add the row to the threat-model "Brokered Capabilities, Never Bearer Secrets" table documenting the one deliberate deviation; (4) extend ADR 0092's threat list with the same item; (5) note the credential in ADR 0024's condensed record.

## Reconciliation with ADR 0113

ADR 0113 commits mobile to foreground-only P2P sync, and ADR 0114 reverses that for one component only: the tether bridge runs as a foreground service while the user has browser access enabled, and the FGS must not start or keep the iroh node alive (bridge-only, enforced in the service implementation). The two transports do not merge: iroh (0113) carries vault sync between enrolled vault devices, authenticated against enrolled device public keys in the git-synced device history; the tether relay (0114) carries request/response unlock traffic between a browser and one phone, where the browser device credential is NOT a vault-enrolled device and its revocation is phone-local, not part of the git device history. An application-layer envelope is required because MV3 service workers cannot run QUIC. Two relays exist for two different protocol families; consolidation is rejected until an iroh-compatible browser transport exists. ADR 0114 is Accepted; ADR 0113 is Proposed. The two decisions do not depend on each other: the tether FGS must not start the iroh node (decision 7), and 0113 stays free to change its transport without reopening this ADR.

## Consequences

- Phone-first users get browser autofill and passkeys against the phone's unlocked state, cross-network, without running a desktop daemon.
- The bridge policy AND its dispatch become one implementation shared by socket and network transports, ending the daemon-only split before it accretes a third caller.
- The extension storage posture changes once, deliberately, with the named threat-model edits above; everything else from ADR 0092 (no vault keys, no tokens, no master password in browser memory; the tether wasm module holds only per-session ephemerals and transport keys) holds unchanged.
- The relay is new attack surface bounded to denial of service; relay-hostile framing in the design doc degrades the feature to "phone unreachable", never to secret exposure. Self-hosting is one command on a machine the user already runs (`baluard relay`, shipped in the existing package trees; the image stays optional for VPS-only users).
- Battery cost on WiFi is estimated negligible (≈ 0.15 %/day net, shell-uid measurement) and confirmed by the dogfood protocol before general availability; cellular is bounded by the adaptive keepalive rather than a fixed 25 s ping; OEM task-killer churn is designed for via cheap per-session re-handshakes.
- Play review carries residual risk around the always-on foreground service; the fallback ladder and the pairing-flow declaration video are prepared up front, and the data-safety/privacy updates are a release gate.
- `bridge.match` loses its uncapped status as part of the same work item, closing the metadata-enumeration hole for the desktop path too; the cap is badge-scale or per-distinct-domain and never auto-revokes on `bridge.match` alone.

## Appendix A: production handshake review scope

Everything below was reviewed by a dedicated third-party design review on 2026-11-20 (verdict CHANGE-FIRST; blockers folded into decisions 3-5 and the items below; review record at the end). Items 1, 2, 3, 5, 6, 7, and 15 are CERTIFIED by design, conditional on the folded wording. Items 4, 8, 9, 10, 11, 12, 14, 16, and 17 are verified-at-code-review gates for the production handshake implementation (build list items 1 and 3), not ADR-status gates. Item 13 is an OPEN DESIGN gate for build list item 4 (pairing ceremony v2): no pairing code lands until a pairing-handshake design note exists and has had the same third-party design review as decision 3.

1. RESOLVED (Spike E, 2026-11-20; pattern switched to NK by the 2026-11-20 review): the stock Noise pattern gives the required properties and is adopted; the custom webnative code is deleted before production tether work begins. Production runs `Noise_NK_25519_ChaChaPoly_BLAKE2s` — IK's initiator-static authentication is KCI-vulnerable (spec §7.7) and a browser-held Noise static cannot stay non-extractable (decision 3). The spike's wasm, CSP, WebSocket, transport-frame, and nonce-echo evidence carries to NK (IK msg1 minus the `ss` term); its IK-specific tests (impostor static, unpinned initiator) do not.
2. Transcript binding: the Noise handshake hash IS the transcript — protocol name, the pre-message phone static, both ephemerals, the payloads, and the msg2 nonce (via its payload). A prologue of `"baluard-tether/v1" || suite_id || pairing_id(16) || rendezvous_id(16)` is hashed in through the snow `Builder` on both ends. The relay URL is deliberately NOT bound: the relay is untrusted, and a pairing may be reached through several equivalent endpoints (public URL, funnel URL, tailnet address). Nothing the relay can alter stays outside the transcript except its own address.
3. Device signature (MANDATORY — the only extension-to-phone authentication, since NK carries no initiator static): `sig_input` = context `"baluard-tether/v1/device-auth"` with a 1-byte length prefix || role tag (0x01 extension, 0x02 phone) || suite_id (1 = Ed25519, 2 = ECDSA-P256-SHA256) || the 32-byte Noise handshake hash; ECDSA-P256 signs `sig_input` with SHA-256. Frame 1 plaintext layout = nonce(32) || signature(64), exactly 96 bytes; any other length closes the session (which fixes item 12's pre-parse gate for frame 1). The signature rides transport frame 1 (counter 0) with the nonce echo; raw 64-byte signatures for both suites (WebCrypto P-256 output is already r||s); pure Ed25519, no prehash. The handshake hash already covers the prologue, both ephemerals, the pre-message phone static, the msg1 timestamp, and the msg2 nonce, so binding anything else separately is redundant. The phone verifies AEAD, echo, and signature, then branches once. MUST before any response carrying credential material: the phone signs its first response frame (role 0x02) and the extension verifies against the pinned phone signing key before accepting any response.
4. DH hygiene: reject all-zero and low-order X25519 outputs; ephemerals are single-use, generated inside the wasm/native snow instance per session, and dropped with the session (in-wasm, not WebCrypto — item 4's old "non-extractable ephemerals" wording is obsolete); public keys are derived from secrets, never by reinterpreting secret bytes (Spike D finding 3).
5. Key schedule: the Noise HKDF-BLAKE2s schedule of the chosen suite — no custom derivation; transport keys come from `Split()`, one per direction; handshake and transport keys never mix.
6. Replay: msg1 payload = version(1) || unix_ms(8), nothing else; the responder rejects skew beyond 30 s, keeps a 60 s cache of seen initiator ephemerals (checked before any DH), and allows one in-flight handshake per rendezvous (garbage msg1 occupying that slot is a DoS only the relay or a rendezvous-ID holder can mount, and the relay can already deny service). The fresh 32-byte CSPRNG nonce rides the msg2 payload; the first transport frame (counter 0) must echo it — the echo is defense in depth, since Noise's fresh responder ephemeral already fails stale-frame AEAD and counter 0 is single-use. Nonce state is per-attempt, consumed on first use, destroyed at a 10 s deadline, never persisted. All failures share one error path (no distinct errors).
7. Downgrade and version: protocol version and suite ID are inside the transcript; no negotiation path to a weaker mode; the P-256 ECDSA signing fallback is a distinct suite ID.
8. Forward secrecy: reproduce the Spike D and Spike E test matrix in production code (impostor responder static; forged or absent device signature; signature from another pairing's key; signature over a different handshake hash; a phone-role signature presented as extension-role; stale and duplicated nonce echo; replayed msg1 against the timestamp and ephemeral cache; msg1 outside the 30 s skew), plus a case where only the phone static key leaks; and two named leak cases: a msg1 forged with only the phone static secret must be rejected at the device-signature step, and recorded transport frames must stay undecryptable after a phone-static-only leak.
9. Leak cases (stated explicitly; the old "IK must keep impersonation requiring its own static key" claim was false for the initiator direction): phone Noise static leak → the attacker can impersonate the PHONE to the extension (NK msg2 needs the phone static) and decrypt recorded msg1 payloads, but cannot impersonate the extension (needs its signing key) and cannot decrypt recorded transport frames (ephemerals die with the session); extension signing-key leak or profile copy → the attacker can impersonate the extension (threat T17) but cannot impersonate the phone. Without the phone signature (item 3), a phone-Noise-static leak would also allow credential injection into the extension. No impersonation property is claimed from the handshake alone for the initiator direction; the signature carries it.
10. AEAD frames: Noise transport messages (ChaCha20-Poly1305 — the recorded exception to the repo's AES-256-GCM invariant, noted in AGENTS.md); per-direction keys from `Split()`; the implicit 64-bit counter is the nonce, so direction and counter protection are structural. Strict next-expected counter, NO reorder window — the counter is the enforcement, not WebSocket ordering (the relay can drop, duplicate, and reorder); any Decrypt failure or oversize frame closes the session with one uniform close code (snow will not do this for you); session hard cap (2^20 frames or 24 h) then close and re-handshake — no rekey code; verify at code review that snow errors at counter exhaustion; frame size cap checked before copying or decrypting.
11. Timestamps: allowed skew stated (30 s); skew failure is shown only in the phone's local UI or log, never as a distinct wire response (item 6: one error path — msg1 is unauthenticated, so a distinct wire response would be an oracle); clock changes cannot rewind counters.
12. Pre-parse gate: verify, decrypt, and check pairing, allowlist, and size before any protobuf or JSON parsing.
13. Pairing ceremony: one-time secret entropy >= 128 bits, 120 s TTL, single use, 3-attempt limit, constant-time compare, the secret is never reused as key material; relay squat and race behavior defined; the QR may carry one or more relay endpoints and the phone dials the first that answers; pinning covers the phone Ed25519 signing key, the phone X25519 Noise static, and the extension Ed25519 signing key; re-pair after rotation is unambiguous. OPEN: the pairing handshake pattern is NOT yet specified — the session pattern presumes pinned Noise statics, which pairing itself establishes; a design note must choose it before pairing code lands (candidates: (a) Noise NX — initiator = extension with an ephemeral only, responder = phone; the QR one-time secret binds via the prologue, which Noise hashes but never mixes into keys, so the never-reused-as-key-material rule holds; the phone static travels in msg2 and is pinned only after on-phone approval; the extension signing public key rides the signed first frame; (b) any pattern needing a throwaway extension static must generate it inside the wasm module, never persist it, and justify the exception in the design note). Using the QR secret as a Noise PSK would reuse it as key material and contradicts the never-reused rule above.
14. Revocation: on revoke, live sessions close immediately and no later handshake succeeds with the revoked keys.
15. JS/browser side: the credential and signature layer stays WebCrypto (one non-extractable signing credential, Ed25519 with a P-256 fallback; no `Math.random`); the channel layer is the snow wasm module (Spike E), and the review covers the wasm-specific surface: the one-import RNG hook backed by `crypto.getRandomValues`, linear-memory scratch zeroization on panic and error paths, and re-initialization on every service-worker wake. Both ends run the same snow implementation, so cross-implementation vectors are structurally satisfied; the review still verifies the suite against the Noise spec vectors.
16. Relay hostility tests: drop, delay, reorder, duplicate, truncate, swap peers, and replay msg1 or the first transport frame across sessions; each ends in "phone unreachable" or a rejected frame, never an executed request.
17. Zeroization: all Rust key material zeroizes on drop; panic paths and error-path logging leak no secrets; wasm linear memory: zero the JS callInOut buffers before free, wrap plaintext copies in `Zeroizing`, drop the wasm instance on session close (in-origin JS can read all wasm memory, so zeroization defends against dumps only).
