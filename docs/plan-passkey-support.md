# Plan: Passkey Support in Baluard

**Status**: Phase 0 complete. Phase 1 next.
**Date**: 2026-06-12
**Author**: TARS (post Esteban's brief)
**Reviewers**: peer review (peer `passkey-review` session, two rounds)
**Goal**: Baluard can **store**, **generate**, and **serve** FIDO2/WebAuthn passkeys for end users. Mobile (iOS + Android) and browser extension clients are the primary delivery surface; the desktop app is the local orchestrator that talks to the daemon.

---

## 1. Why now

Baluard's mobile and browser extension clients are early-stage (extension is a SolidJS skeleton, mobile is Kotlin Multiplatform scaffolding). The product narrative is "your vault on your devices, no server." Passkeys are the modern replacement for password autofill, and the only way to be a credible autofill vault on iOS/Android/browser in 2026 is to act as a WebAuthn platform/roaming authenticator. This plan defines the minimum viable passkey support, plus the path to cross-device assertion.

We are **not** building a FIDO2 server (no cloud). Baluard is a **software authenticator** that lives inside the user's encrypted vault. The private key for each passkey is generated and held in daemon memory after unlock, never crosses IPC, signs challenges on demand. Counter and credential metadata are persisted in the encrypted cipher envelope.

**Review history**:
- v1: initial research and analysis
- v2: incorporated the first peer review. Major changes: `passkey-rs` evaluation moved to Phase 0 (was deferred); Linux user verification strategy decided (master password re-prompt); conditional mediation added as hard Phase 2 scope; counter git-sync `max()` strategy added; extension `world: "MAIN"` for CSP-strict sites; mobile architecture committed to UniFFI library (no daemon process on mobile); `PasskeyUseModal` deferred to Phase 2; local `webauthn-rs` RP test harness added as hard deliverable.
- v3: incorporated the second peer review. Approved with fixes. Changes: removed `discoverable: bool` field (invariant is not data); removed contradictory `web_accessible_resources` line in §4.7; added explicit `residentKey: "required"` + `requireResidentKey: true` + `userVerification: "required"` to `authenticatorSelection`; made `coset`/`ciborium` deps conditional on `passkey-rs` rejection; made `uniffi` interface synchronous; added fresh-KDF-verify constraint to Linux UV substitute; rewrote Phase 3 scope to remove stale "Daemon IPC over local network" text contradicting the UniFFI decision; clarified counter race risk as inherent to all synced passkey implementations (not Baluard-specific).

## 2. Spec Recap (research, not plan scope)

### 2.1 W3C WebAuthn Level 2/3 + FIDO2 CTAP 2.1

Two ceremonies, both client-driven from the browser/mobile OS:

| Ceremony | Browser API | Result |
|---|---|---|
| Registration | `navigator.credentials.create({ publicKey })` | Attestation object (CBOR), public key, credential ID |
| Assertion | `navigator.credentials.get({ publicKey })` | Signature over challenge + authenticatorData |

**Key data structures**:

- `AuthenticatorData` (binary): `rpIdHash || flags || signCount || attestedCredentialData (registration only) || extensions`
- `ClientDataJSON`: JSON, base64url-encoded, contains `type`, `challenge` (base64url), `origin`, `crossOrigin`
- `AttestationObject` (CBOR, registration only): `fmt`, `attStmt`, `authData`
- COSE-encoded public key (per [RFC 8152]): algorithm-tagged, supports `ES256` (-7), `EdDSA` (-8), `RS256` (-257), `PS256` (-37)
- `credentialId`: opaque, generated by authenticator, min 16 bytes with 100 bits entropy

**Algorithms Baluard should support**: `ES256` (P-256 ECDSA, default), `EdDSA` (Ed25519, modern preferred). RS256/PS256 are legacy and add little value for a software authenticator that controls its own key material.

**AAGUID**: identifies the authenticator model. Baluard should have a stable AAGUID (one per platform family: `baluard-desktop`, `baluard-mobile`, `baluard-extension`).

**RP ID**: domain string, scoped per relying party. WebAuthn requires RP ID == origin's effective domain or a registrable domain suffix. Stored per-credential.

**Discoverable (resident) credentials**: passkeys are discoverable by default. We do not need to support non-discoverable.

**Sign count (counter)**: monotonic counter used to detect cloned authenticators. Increments on every assertion. Stored in encrypted cipher metadata.

**PRF extension** (WebAuthn L3): `hmac-secret` for deriving a key per site (useful for E2EE with sites that support it). Add as stretch goal.

### 2.2 Where the spec puts complexity

The protocol is simple on paper. The implementation is intricate because of:
- COSE public key encoding (CBOR map with numeric tags)
- AuthenticatorData layout (binary, byte offsets matter)
- CBOR canonical encoding rules (CTAP2 canonical form)
- Base64url everywhere (no padding)
- Attestation statement format parsing (we can skip verification — Baluard attests to itself, `fmt = "none"` is acceptable for self-attested software authenticators)

## 3. Reference architectures (analysed)

### 3.1 Bitwarden

Storage model (decided in [PM-3807](https://github.com/bitwarden/clients/pull/6255)): passkeys are stored as `CipherType.Login` with an optional `fido2Credentials[]` array. Each element:

```ts
// libs/common/src/vault/models/view/fido2-credential.view.ts
{
  credentialId: string,        // base64url
  keyType: "public-key",
  keyAlgorithm: "ECDSA",       // only ECDSA in their model
  keyCurve: "P-256",
  keyValue: string,            // COSE-encoded public key, base64url
  rpId: string,
  userHandle?: string,         // base64url
  userName?: string,
  counter: number,
  rpName?: string,
  userDisplayName?: string,
  discoverable: "true" | "false",
  creationDate: Date,
}
```

The **private key is not stored** in the cipher. It is generated and held in the platform authenticator (TPM, Secure Enclave, Keychain) during registration and used to sign assertions. The cipher only stores the public key. On assertion, the client asks the platform authenticator to sign, and verifies the signature against the stored public key on the server (or locally).

**Server endpoints** (C# `WebAuthnController.cs`):
- `GET /webauthn` — list user's WebAuthn login credentials (this is for passkey-as-2FA, not passkey-vault)
- `POST /webauthn/attestation-options` — generate challenge + RP options
- `POST /webauthn/assertion-options` — generate challenge + allowCredentials
- `POST /webauthn` — store registered credential
- `PUT /webauthn` — update credential (PRF key set)
- `POST /webauthn/{id}/delete` — remove

Two distinct WebAuthn use cases in Bitwarden:
1. **Passkey login** (2FA replacement): credentials stored in the user's account, private key in platform authenticator
2. **Stored passkey** (vault item): credentials stored in cipher, private key in platform authenticator, used to autofill relying parties

We are implementing case 2. Case 1 is a possible future feature (Tier 2 from `docs/2fa-analysis.md`).

**Browser extension fido2 bridge** (484 LOC `fido2.background.ts`):
```
content script (page-script.js) ← page's navigator.credentials.create/get
   ↕ message via chrome.runtime.Port
background (fido2.background.ts)
   ↕ message
Fido2ClientService → AbortController
   ↕
native messaging → windows_plugin_authenticator.dll (Chromium subprocess) or
                   NAPI → win_webauthn/mac_authenticator/iOS via FFI
```

`windows_plugin_authenticator` is a Rust crate implementing a Chromium CDM-style plugin; it talks to Windows WebAuthn API (`webauthn.dll`).

`win_webauthn` is a Rust crate that wraps the Windows WebAuthn API (in `apps/desktop/desktop_native/win_webauthn/`). It produces AuthenticatorData and attestation objects by calling the OS, then ships them back via NAPI to the Electron desktop client.

For **macOS/iOS**, Bitwarden calls the native `LocalAuthentication` framework and `Security.framework` (SecAccessControl with `.biometryAny`) to wrap the private key in the Secure Enclave. There is no separate Linux passkey authenticator — they fall back to the platform's own FIDO2 stack via CTAP2 over USB/BLE/NFC, or use the browser's built-in authenticator.

For **mobile** (`src/App/Platforms/Android/Autofill/Fido2*UserInterface.cs` and iOS), the OS's own platform authenticator is used; the mobile app is a thin bridge between the Android AutoFill framework or iOS AutoFill credentials provider and the daemon.

### 3.2 Vaultwarden (Rust reference, server-side)

Uses [`webauthn-rs`](https://github.com/kanidm/webauthn-rs) v0.5.5 with feature flags:
```
webauthn-rs = { version = "0.5.5", features = ["danger-allow-state-serialisation", "danger-credential-internals"] }
webauthn-rs-proto = "0.5.5"
webauthn-rs-core = "0.5.5"
```

Single 518-LOC file `src/api/core/two_factor/webauthn.rs`:
- Lazy `static WEBAUTHN: Webauthn` built from `CONFIG.domain()` (RP ID = effective domain of vault host)
- `WebauthnBuilder::new(rp_id, rp_origin).rp_name(...).timeout(...)`
- Routes: `get-webauthn`, `get-webauthn-challenge`, `activate-webauthn`, `activate-webauthn-put`, `delete-webauthn`
- `start_passkey_registration(uuid, email, display_name, existing_cred_ids)` returns `PasskeyRegistration` (public key + state)
- `finish_passkey_registration(&state, &RegisterPublicKeyCredential)` returns `Passkey`
- `start_passkey_authentication(&[Credential])` returns `PasskeyAuthentication` (challenge + state)
- `finish_passkey_authentication(&state, &PublicKeyCredential)` returns `AuthenticationResult`
- `Passkey` stored in `two_factor` table JSON column as `WebauthnRegistration { id, name, migrated, credential: Passkey }`
- U2F → WebAuthn migration helper (separate path, can ignore for Baluard)

**Important**: Vaultwarden uses webauthn-rs as a **relying party server** — it accepts registrations and verifies assertions. Baluard needs to be the **authenticator**, which is the same library but called from the other side. The `webauthn-rs` API surface is symmetric enough that this is workable, but we need to write (or find) an `Authenticator` trait implementation that:
- Generates credential key pairs (in-process, never leaves memory)
- Produces `AuthenticatorData` for both registration and assertion
- Signs `authData || clientDataHash` with the credential private key
- Maintains sign count per credential

There is **no first-party "webauthn-rs-authenticator"** crate. The standard pattern is to:
1. Use `webauthn-rs-proto` for the wire types (`AuthenticatorAttestationResponseRaw`, `RegisterPublicKeyCredential`, etc.)
2. Use `coset` or hand-rolled CBOR for COSE public key encoding
3. Use `ed25519-dalek` and `p256` for signing
4. Implement ceremony logic in ~600 LOC

**Better alternative**: [`passkey-rs`](https://github.com/1Password/passkey-rs) is the **1Password**-maintained Rust crate implementing the authenticator side of the ceremony. Not "small community" — used in 1Password's own product. Includes `passkey-authenticator` (ceremony state machine + credential storage), `passkey-client` (simulated platform client, useful for integration tests), `passkey-types` (wire types), and `public-suffix` (RP ID validation). Evaluate in Phase 0 before any hand-rolling. See §5 Phase 0.

### 3.3 Differences between Vaultwarden model and what Baluard needs

| Aspect | Vaultwarden | Baluard |
|---|---|---|
| Role | Relying Party server | Authenticator (also acts as relying party for `extension ↔ daemon` loopback) |
| Storage | Plaintext DB row per credential | Encrypted inside vault cipher envelope |
| Private key | Lives in user's hardware authenticator | Lives in daemon memory; persisted only as encrypted private key in cipher |
| Multi-device | One credential per user, used for 2FA | One credential per (RP, account) per device, syncable via git |
| AAGUID | N/A (server only) | Baluard's own AAGUID per platform |
| Attestation | Server validates `fmt: "packed"` / `"tpm"` etc | We self-attest with `fmt: "none"` (we control both ends) |

## 4. Baluard impact surface

### 4.1 Cipher schema (Rust core)

**File**: `crates/baluard-core/src/types.rs`

Add:
- `CipherType::Passkey` variant
- `PasskeyData` struct mirroring Bitwarden's fido2 credential fields, plus:
  - `private_key: EncryptedPrivateKey` — the credential's private key, wrapped under the cipher item key
  - `aaguid: Uuid` — which Baluard platform produced this
  - `user_handle: Option<Vec<u8>>` — RP-assigned user handle
  - `discoverable: bool` — always `true` for Baluard. **Drop the field entirely** — an invariant is not data, it's a documentation claim that future code will branch on expecting variation. Discoverability is enforced by always sending `residentKey: "required"` in `authenticatorSelection` (see §4.5).
  - `prf_key: Option<EncryptedPrfKey>` — for the PRF extension
  - `linked_login_id: Option<Uuid>` — points to a `CipherKind::Login` for the same RP, for UX deduplication. Set when the user creates the passkey from inside an existing Login detail view; `None` if created standalone.
- `CipherKind::Passkey(PasskeyData)` variant in the tagged enum
- `CipherType::Passkey` in the cipher_type enum
- Update `cipher_type()` and `match` in `resolve_linked_field` (passkey has no linked fields)
- `CipherMeta` and `CipherInput` already use `CipherKind` so no structural change

**Note on `private_key`**: This is a divergence from Bitwarden. We store the private key encrypted inside the cipher (Bitwarden does not, because it relies on platform authenticators). For a cross-device flow, this is necessary: the same passkey must sign on desktop, mobile, and extension. Storing it encrypted under the item key is consistent with how TOTP secrets and SSH private keys are stored today. Item key never crosses IPC. Private key is decrypted to memory on demand, used to sign, zeroized.

**Epoch rotation**: `revoke_device_and_rekey()` re-encrypts all cipher envelopes under the new epoch. Passkey ciphers participate like all other ciphers — the wrapped `private_key` is re-wrapped under the new item key. No special handling required. The plan must call this out explicitly: do not "optimize" rotation to skip passkey ciphers, or you will silently lose every passkey. Add a unit test that asserts passkey ciphers survive `revoke_device_and_rekey()`.

**Tier**: Passkey ciphers will typically fit in `Xs` (5KB) — the metadata is small, no URIs, no notes. The private key is 32 bytes (Ed25519) or 32 bytes (ES256 scalar), COSE public key ~80 bytes, all metadata < 1KB serialized.

### 4.2 Vault CRUD

**File**: `crates/baluard-core/src/vault/cipher.rs`, `handle.rs`

- `add_cipher` / `update_cipher` already accept `CipherInput` JSON; the new `Passkey` variant flows through with no handle changes
- `list_cipher_meta` returns `CipherMeta` which already carries `cipher_type`. Add `display_name` extraction (use `rp_id` for passkeys).
- `delete_cipher` works as-is.
- Counter updates flow through the existing `update_cipher` route. The counter is inside the encrypted envelope; there is no meaningful optimization in having a separate route — the full cipher must be decrypted, counter incremented, re-encrypted, and written. A dedicated `passkey_counter_increment` route would be a race magnet and an asymmetric API surface. Drop it.

### 4.3 Import / Export

**File**: `crates/baluard-core/src/import/bw_json.rs`

Currently `fido2_credentials: Option<serde_json::Value>` is captured as raw JSON and dropped. Replace with typed parse: extract Bitwarden's Fido2Credential fields, but **private key is not in BW export** — we'd need to mark these passkeys as `private_key_missing: true` and refuse to serve them for assertion. They are viewable metadata only until the user re-registers.

**Phase 0 deliverable**: read-only import of BW passkey metadata.

Export: emit `fido2_credentials[]` in BW JSON format. Round-trip with BW. Private key included (BW ignores it; we encrypt at rest anyway).

### 4.4 Crypto (no new primitives)

Existing primitives cover everything:
- `ed25519-dalek` — EdDSA signing
- `p256` — ES256 signing
- `coset` (new dep, ~300KB) — COSE key encoding/decoding
- `cbor4ii` or `ciborium` (new dep) — CBOR for attestation object, AuthenticatorData
- AES-256-GCM (existing) — wrap the private key under the cipher item key

WebAuthn ceremony implementation: ~600 LOC, isolated in `crates/baluard-core/src/crypto/webauthn/`. No changes to root key, item key, or epoch system.

### 4.5 Daemon IPC

**File**: `crates/baluard-daemon/src/handler.rs`

Add routes (JSON-in-string `GatewayRequest.payload`):

| Action | Direction | Purpose |
|---|---|---|
| `passkey.challenge_register` | desktop → daemon | `{rp_id, rp_name, user_name, user_display_name, user_id}` → `{publicKey, state}` (PublicKeyCredentialCreationOptions JSON). The daemon's response sets `authenticatorSelection: { residentKey: "required", requireResidentKey: true, userVerification: "required" }` always. |
| `passkey.finish_register` | desktop → daemon | `{name, attestation_response, state}` → `Passkey cipher` |
| `passkey.challenge_assert` | desktop → daemon | `{rp_id, allow_credentials?}` → `{publicKey, state}` (PublicKeyCredentialRequestOptions JSON) |
| `passkey.finish_assert` | desktop → daemon | `{assertion_response, state}` → `{verified: bool, cipher_id, sign_count}` |
| `passkey.list` | desktop → daemon | `{}` → `[PasskeyMeta]` |
| `passkey.delete` | desktop → daemon | `{cipher_id}` → `{}` |
| `passkey.rename` | desktop → daemon | `{cipher_id, name}` → `{}` |

State management: registration/assertion `state` is a short-lived, in-memory map keyed by `state_id` (random 128-bit). **300-second TTL** (matches Chrome's WebAuthn user-interaction timeout — 60s is too short for users who fail a biometric once and retry). On finish, state is consumed. On timeout, evicted. This matches `webauthn-rs` semantics.

**Token-gated**: all routes require session token (existing pattern).

**Private key never serialized over IPC**. The cipher on disk has the encrypted private key; the daemon decrypts it on `finish_register`/`finish_assert` calls, keeps the plaintext in a `Zeroizing<Vec<u8>>` for the duration of the call, zeroizes on drop. No persistent in-memory cache of private keys (defense in depth — if the daemon process is dumped, only the current call's key is exposed, not the entire fleet).

### 4.6 Desktop (Tauri/SolidJS)

**Files**: `desktop/src/components/Passkey*.jsx`, `desktop/src/lib/passkey*.js`

UI:
- New cipher type in `VaultView` categories: passkey icon, list filter
- `PasskeyDetail.jsx`: shows rp_id, rp_name, user_name, user_display_name, creation date, last used. Delete/rename.
- `PasskeyCreateModal.jsx`: user pastes an `origin` URL (e.g. `https://example.com`) or clicks a "From this site" button (populated from active tab in extension, or manually in desktop). Daemon generates challenge. App shows OS-level biometric prompt (Touch ID / Windows Hello). On success, store cipher.
- `PasskeyUseModal.jsx`: shown when a relying party requests an assertion and there's a candidate. List matching passkeys, user picks one, biometric prompt, signature returned.

Toast for all passkey operations. All modals use existing `<FocusTrap>`.

### 4.7 Browser extension (SolidJS)

**File**: `extension/` (currently a 287-byte package.json)

The extension is the WebAuthn entry point for desktop browser autofill. The flow:

```
[web page] navigator.credentials.create()  →  [content script: page-script.js]
                                                  ↕ inject script + window.postMessage
[content script: fido2-content-script.ts]
                                                  ↕ chrome.runtime.connect("fido2.background")
[background: fido2.background.ts]
                                                  ↕ native messaging
[native host: baluard-extension-helper binary]
                                                  ↕ Unix socket (token-gated)
[Baluard daemon]
```

**Phase 2 deliverable**:
- `extension/manifest.json` (MV3)
- `extension/src/page-script.js` — injected into every page, intercepts `navigator.credentials.create` and `.get` by replacing them with proxies that post messages to the content script. **Must use `chrome.scripting.executeScript` with `world: "MAIN"`** in the content script's registration, NOT a `web_accessible_resources` `<script>` tag. CSP-strict sites (GitHub, banking) block the latter. `world: "MAIN"` injects into the page's main JS world but is exempt from page CSP because it is extension-owned.
- `extension/src/content-script.js` — bridges page-script ↔ background via `chrome.runtime.connect`
- `extension/src/background.js` — routes to native messaging host
- `extension/src/popup/` — passkey picker UI (SolidJS)

**Conditional mediation** is a hard Phase 2 requirement. Modern sites (GitHub, Google) call `navigator.credentials.get({ mediation: "conditional" })` to request passkeys as inline autofill in the username field, not as a popup. The extension's `page-script.js` must detect this mediation mode and surface matching passkeys into the browser's autofill suggestion list, not just the explicit `PasskeyUseModal` path. Without it, Baluard passkeys will feel broken on every site that uses modern passkey UX. The Bitwarden extension's `fido2-autofill-utils.ts` is the reference pattern (it pre-filters by `rpId` and username, and injects `<input>` autocomplete entries).

Native messaging host: small Rust binary in `extension/native-host/` (or a new crate `baluard-extension-host`) that speaks the Chromium native messaging protocol (JSON over stdio, 4-byte length prefix) and forwards to the daemon over the existing Unix socket with the session token.

**Permissions needed in manifest**: `nativeMessaging`, `<all_urls>` (for the content script), `tabs` (for origin lookup), `storage` (for caching RP ID hints).

**Do not declare `web_accessible_resources` for the page-script.** That would imply the alternative `chrome.runtime.getURL` injection pattern, which is exactly what `world: "MAIN"` replaces. Extension-owned scripts injected via `chrome.scripting.executeScript({ world: "MAIN" })` are exempt from page CSP; web-accessible files are not. Pick one approach, not both.

### 4.8 Mobile (Kotlin Multiplatform)

**File**: `mobile/` (currently KMP scaffolding for iOS + Android)

The mobile app is a second WebAuthn entry point. The OS-level integration is what makes this work — the user does not need to open Baluard explicitly:

**Android (Credential Provider Service)**:
- Service registered in `AndroidManifest.xml` as `android.app.role.RoleManager.ROLE_CREDENTIAL_PROVIDER`
- Implements `CredentialProviderService` from `androidx.credentials`
- In `onBeginGetCredential`, query the daemon (over a Baluard-on-device socket or BLE to desktop) for passkeys matching the origin
- Return `PublicKeyCredentialEntry` for each candidate
- On user selection, the system calls back with the request, we forward to the daemon for signing, return `PublicKeyCredential` to the framework
- Phase 3 deliverable: ~400 LOC Kotlin + daemon-bridge glue

**iOS (ASCredentialProviderViewController)**:
- AutoFill Credential Provider extension
- Implements `ASCredentialProviderViewController.prepareInterfaceToProvideCredentials`
- Query the daemon (over local network, BLE, or USB) for candidates
- Return `ASPasskeyCredential` for each
- On selection, the extension's `prepareInterfaceForExtensionConfiguration` is invoked with the credential request
- Forward to daemon, sign, return assertion
- iOS 17+ supports passkey AutoFill natively
- Phase 3 deliverable: ~400 LOC Swift + KMP bridge

**Mobile architecture decision**: mobile runs `baluard-core` as a library via Rust FFI (UniFFI), linked into the Kotlin Multiplatform app. There is **no daemon process on mobile** — iOS background-execution constraints make a long-running Unix socket daemon infeasible, and Android equivalents are even worse. The mobile app has its own copy of the vault, synced via git like every other device. AutoFill requests are answered by an in-process FFI call to `baluard-core`, not by a socket roundtrip. This means cross-device (Phase 4) is the only case where mobile needs to talk to desktop, and that uses the QR pairing channel — a one-shot local connection, not a persistent daemon.

Kotlin/Swift code is glue only: query the FFI for matching passkeys, format them as `PublicKeyCredentialEntry` (Android) or `ASPasskeyCredential` (iOS), forward the system callback back to the FFI for signing. The cryptographic ceremony never leaves Rust.

**Cross-device flow** (caBLE / hybrid transport): the relying party is on a desktop browser, the user's passkey is on their phone. The protocol uses:
1. `hybrid` transport in `authenticatorSelection` during registration/assertion
2. The phone receives a notification via FIDO Alliance's hybrid transaction transport (BLE advert + encrypted tunnel)
3. The phone's authenticator (Baluard) signs and returns over the encrypted channel

The FIDO Alliance's hybrid transport requires a **cloud relay** for the initial handshake. **Baluard has no cloud.** Two options:
- (a) Implement a simplified local-only hybrid: BLE advertisement on the phone, the desktop browser extension listens for it, sets up a local encrypted channel. Skip the cloud relay. Works only when both devices are BLE-reachable.
- (b) Require the user to scan a QR code (analogous to WhatsApp Web) to establish the channel. QR code encodes a one-time pairing token.

**(b) is the right MVP.** The phone shows a QR code on request; the desktop scans it with the extension; they establish a local channel; passkey assertion completes. This is what Bitwarden does not do (they punt on cross-device entirely for individual passkeys; they only support same-platform).

**Scope clarification (must be in Phase 4 user-facing docs)**: this cross-device path works **only when the Baluard browser extension is installed and active on the desktop browser**. It does NOT work with native OS passkey dialogs (Chrome's Android passkey sheet, Safari's iOS passkey sheet) — those bypass the extension entirely and require the FIDO Alliance cloud relay we do not implement. Mobile OS users who tap a native passkey prompt will not see Baluard in the system picker. This is an honest scope limit, not a Phase 4+ bug.

## 6. Open questions (Phase 0 resolves, rest is open)

**Resolved in Phase 0** (no longer open):
1. `passkey-rs` vs hand-rolled ceremony: ✅ `passkey-rs` 0.5.x adopted. ADR at `docs/adr/0007-passkey-rs-evaluation.md`. Registration + assertion round-trip through webauthn-rs verified.
2. Linux user verification: ✅ Re-prompt master password with fresh KDF verify. Documented UX downgrade.
3. Mobile architecture: ✅ `baluard-core` as a library via UniFFI, no daemon process on mobile.
4. Counter git-sync conflict: ✅ `merge_counter = max(local, remote)` per-cipher. After sync, stored counter is `max(local, remote)` before the next assertion; authenticator always writes `counter + 1` at assertion time.

**Still open** (carry into Phase 0/1):
1. **Self-attestation vs none-attestation**: spec allows `fmt: "none"` for software authenticators that don't want to be tracked. We should use `none` and ship our own AAGUID for analytics/reputation, but skip attestation certificate chains entirely. **Recommendation**: use `none`, ship AAGUID. (FIDO Alliance consumer sites — GitHub, Google, Cloudflare — accept `none`. Enterprise RPs with attestation enforcement are not V1 users.)
2. **Storage of `private_key`**: encrypted under item key (current proposal) vs derived deterministically from master password + cipher ID (deterministic, no extra key wrap). **Recommendation**: encrypted under item key, matches SSH/TOTP pattern in current code.
3. **Counter persistence**: encrypted in cipher envelope (current proposal) vs plaintext in cipher metadata (faster, no decrypt on every assertion). **Recommendation**: encrypted. Counter is part of cipher authenticity, can't be tampered with.
4. **Touch ID / Windows Hello gating**: every assertion requires user verification. **Recommendation**: yes, `UserVerificationPolicy::Required` always. No UV == no signing. This is the security guarantee. (Linux exception: master-password re-prompt is the substitute; document the difference.)
5. **Interaction with `docs/2fa-analysis.md` Tier 2**: that doc proposes using FIDO2 *for vault unlock*. This plan is about FIDO2 *as a stored item*. They are independent and both are planned. Tier 2 becomes a separate plan after this one lands.
6. **Browser extension safety**: an extension that intercepts WebAuthn on every page is a fingerprinting/tracking concern. **Recommendation**: extension is opt-in, only active when `enable_passkeys` is true. Show a clear visual indicator when active. Same model as 1Password and Bitwarden.
7. **Mobile ↔ desktop passkey use**: when mobile is not on the same network as desktop, how does the mobile auto-fill reach a passkey that's only on the desktop? **Recommendation**: Phase 3 requires the passkey to be synced to the mobile device. Cross-vault passkey use is a Phase 4+ feature.
8. **Backward compatibility of cipher schema**: adding a new `CipherKind` variant is backward-compatible for serialization (existing clients ignore unknown variants). Deserialization is also tolerant as long as we add the new variant to the default fallback chain. **Recommendation**: `#[serde(default)]` on `PasskeyData`; do not set `Passkey` as the default kind. **No migration needed for existing vaults.**

## 7. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Browser extension fingerprinting / abuse | High | High | Opt-in only, visible indicator, no background WebAuthn interception when disabled |
| iOS/Android AutoFill framework changes | Medium | High | Abstract daemon IPC behind an interface; mobile code is isolated to ~800 LOC total |
| Cross-device relay abuse (someone else pairing) | Medium | High | QR code must be scanned within 30s; pair codes are single-use; require biometric on both ends |
| Counter not atomic across devices (git sync) | Medium | Medium | Sync engine applies `merge_counter = max(local, remote)` per passkey cipher when both sides have advanced. The spec only requires `counter_new > counter_stored` (not `+1`), so `max()` is monotonic. **Residual inherent risk**: two devices both sign before syncing emit assertions with the same counter; one is rejected by the RP. This is not Baluard-specific — Apple, Google, 1Password all have this property with synced passkeys. FIDO Alliance guidance now recommends RPs accept counter=0 and not reject counter-non-monotone assertions without additional cloning evidence; GitHub, Google, Cloudflare all follow this. Regression test in Phase 1: simulate concurrent assertions on two devices, verify vault counter never regresses after merge. |
| WebAuthn ceremony implementation bugs (interop with RPs) | High | High | Hard Phase 1 deliverables: local `webauthn-rs` RP harness as in-process test, FIDO Alliance test vector corpus, `proptest` for COSE/AuthenticatorData, 80%+ coverage. Manual QA on github.com, google.com, cloudflare.com is smoke test only, not acceptance. |
| **Mobile native OS passkey dialogs are invisible to Baluard** (cross-device scope) | Certain | Medium | Document explicitly in Phase 4 user-facing docs. Chrome Android passkey sheet and Safari iOS passkey sheet bypass the extension; Baluard will not appear. Workaround: use the Baluard browser extension on desktop for cross-device, or rely on synced passkeys on the mobile device itself. |
| Linux UV has no hardware path (master password re-prompt is the substitute) | Certain | Low | Documented UX downgrade. Re-prompt step is added to the ceremony on Linux. Fixed when platform UV becomes available. |
